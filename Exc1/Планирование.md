# Планирование: анализ, идентификация проблем и поиск решений

## Анализ схемы и описания системы

Существующие и потенциальные проблемные места:

 - Клиенты жалуются менеджерам по продажам, что они не получили заказ и над их изделием работают уже несколько месяцев, хотя обещали закончить за три недели. 
   Проблемы не на стороне производства: производственные мощности позволяют справиться с заказами и могут обеспечить двукратный рост.
 - После открытия API, который MES использует для расчёта стоимости изделия, а заказ создаётся в CRM через получение сообщения из очереди от MES 
   жалоб от клиентов на просроченные заказы стало ещё больше. Добавились жалобы со стороны пользователей API. Компании сообщают, что не получили свои заказы.
 - Тормоза в интерфейсе: у операторов MES система долго грузит страницу со списком заказов с их статусами. 
 - Ручное тестирование и CI/CD релизов - замедление выхода прода
 - Судя по описанию статусов заказа, статусы выставляются в разных системах в своих БД. 
 - Межсистемного опроса или оповещения нет. Изменение межсистемных контрактов представляется трудоемким
 - Отсутствует единая точка входа для запросов от внешних систем и пользователей, что усложняет поддержку и понижает уровень безопасности программного продукта
 - CRM API и Shop API разделяют одну БД, что противоречит паттерну Database per service
 - Не соблюдается паттерн Distributed tracing, поэтому нет возможности отслеживать ход выполнения внешних запросов внутри программного продукта, оценивать и предсказывать уровни нагрузки
 - Отсутствие наблюдаемости системы не позволяет определить проблемные места
 - Отсутствует балансировщик нагрузки и сервис регистрации систем, что не позволяет гибко управлять нагрузкой на системы


### Вывод:

Для того, чтобы делать какие-то выводы по главной проблеме программного продукта - потеря заказов - необходимо внедрить мониторинг, 
провести мероприятия по устранению отсутствия наблюдаемости, обеспечить соблюдение паттерна Distributed tracing. 
Для этого необходимо обеспечить соблюдение паттернов API-шлюз, Database per service.
Для устранения медленной загрузки заказов с их статусами целесообразно организовать кэширование новых заказов 
на фронтенде с программной инвалидацией по факту добавления заказов.

## Инициативы для устранения нежелательных ситуаций

Список инициатив в порядке приоритета:

 - Внедрить мониторинг, логирование, трейсинг - чтобы найти причины проблем
 - Внедрить APISIX Gateway(+Consul), выполняющий функции маршрутизации внешних запросов, аутентификации, регистрации систем и балансировки нагрузки
 - Отвязать Shop API от БД CRM API, направить поток данных Shop API на брокер сообщений, подписчиком сделать CRM API
 - Доработать системы для отправки и получения по подписке сообщений о смене статуса.
 - Добавить кэш списка заказов
 - Добавить BFF-сервисы для партнеров и интернет-магазина
 - Разнести чтение заказов и их расчет (с записью в базу) на разные микросервисы
 - Добавить реплику базы MES для чтения списка заказов
 - Добавить очередь между API User и MES API
 - Добавить реплику Shop DB для разделения чтения и записи
 - Добавить инстансы Shop API

 В ближайшие полгода необходимо выполнить первые пять пунктов из списка инициатив, это должно решить основную проблему с потерей заказов
и наметить пути для увеличения наблюдаемости и ускорения работы системы.
